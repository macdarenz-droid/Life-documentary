# T-011 · P6 Upload queue and sync

Text for T-011a–e. Published 2026-09-27; this file does not change after publication. Fix lists are written in `tasks/TASKS.md` under the task.

## Preamble

**Goal of P6.** A signed-in phone keeps its documentary's rows in step with the server and uploads what the service may see, and nothing else. One shared rule, `leavesDevice`, decides on both sides what may leave: a `localOnly` moment never leaves in any form (not its row, not its media). Rows sync with `POST /sync` (a cursor, last-write-wins per row, tombstones, a change log). Media upload in 5 MiB parts streamed through the Worker into R2 (D34), resumable across restarts, with backoff and a Wi-Fi rule for video. In P6 only what the service needs to understand a week leaves the device (previews and answers); full originals leave only when a later phase asks for them (P12 requests, P23 Cloud backup).

**Read first:** `CLAUDE.md` (rules 2, 3, 5, 6, 8, 9, 10), `docs/VISION.md` §8, `docs/architecture/ARCHITECTURE.md` §3, §5 "Upload" and "Sync", §6, §7, DECISIONS D14, D15, D16, D33, D34, D36, D37, `tasks/p4/T-010.md` (sessions, the first link, contracts on both sides).

**Stack (checked 2026-09-27).**
- R2 binding (Workers types in `apps/api/worker-configuration.d.ts`): `env.MEDIA.createMultipartUpload(key, { httpMetadata, customMetadata })` → `{ key, uploadId, uploadPart(n, value), complete(parts), abort() }`; `resumeMultipartUpload(key, uploadId)`; `uploadPart` takes a `ReadableStream` of known length, an `ArrayBuffer(View)`, a string or a `Blob`, and returns `{ partNumber, etag }`. Every part but the last must be at least 5 MiB and all non-final parts the same size. It runs in the Workers test pool (Miniflare).
- Mobile (`npx expo install`): `expo-network` ~57.0.2 (`getNetworkStateAsync()` → `{ type: NetworkStateType.WIFI | CELLULAR | …, isConnected, isInternetReachable }`), `expo-background-task` ~57.0.20 with `expo-task-manager` ~57.0.20 (`TaskManager.defineTask(name, fn)` at module scope, then `BackgroundTask.registerTaskAsync(name, { minimumInterval /* minutes, at least 15 */ })`; iOS runs it when the system chooses). HTTP bodies go through `expo/fetch` (check in its types that it takes a `Uint8Array` body; if not, name the closest honest option under Risks).
- D1 (research 2026-09-26): at most 100 bound parameters per statement, `batch()` is one atomic transaction, no `BEGIN`/`COMMIT`.

**Decided here (DECISIONS D37).**
- **Last-write-wins per row in v1**, not per field: every synced row carries `updatedAt`; the server keeps an incoming row only when its `updatedAt` is later than the stored one (ties: the stored row stays). While a documentary has one writer (solo, until crew in P19) per-row and per-field give the same result; P19 revisits per-field. D16 is updated to say so.
- **What syncs.** Documentary, moments, the synced part of media assets, questions, storylines, cast members. Device-only fields never leave: `localPath`, `wrappedKey`, `posterPath`, `posterWrappedKey`. The server stores a moment's storyline and cast ids as JSON arrays (it needs no join tables yet).
- **What uploads in P6** (`leavesDevice(moment, { cloudBackup: false })`): `localOnly` → nothing at all. Otherwise: the row syncs; an **answer** uploads its media as it is (a 10-second video or voice answer is small, and the service needs its sound for the transcript in P12); a **photo** uploads a preview (longest side 1,000 px, JPEG 0.8), not the original; a **clip** from the library uploads nothing yet (its keyframe preview comes with P12, the clip itself when an episode asks for it); a note has no media. `original: true` only with `cloudBackup` (P23), so never in P6.
- **R2 layout.** `u/{userId}/{documentaryId}/{assetId}/{purpose}` with `purpose` `preview` or `answer` or `original`; previews and answers are the service's working copies, deleted after P12 writes their text (the 2-day `tmp` lifecycle rule of D14 is an owner deploy item).
- **One phone holds the media in v1.** A pulled media asset only updates an asset this phone already has (its `cloudKey`); a pulled moment whose media is not on this phone is not stored locally (the local contract needs a local file), so a second phone gets the documentary, storylines, cast, questions and notes but not other phones' media moments. Showing cloud-only moments is later work.
- **Cellular.** Video (answers) waits for Wi-Fi; photos' previews and voice answers go on any network. A Settings switch to allow video on cellular comes with P23.

**Rules for every P6 task.** `leavesDevice` is called before a row is put in a sync payload, before an upload is enqueued, and again on the server before a row or a part is accepted (rule 8); a test on each side proves a `localOnly` moment is refused. Every body is a contract parsed on both sides. The API never trusts ids across users: every route checks that the documentary belongs to the session user. No test logs a cookie, a key or file bytes.

**Out of scope.** Full-original uploads and the server asking for them (P12), Cloud backup and its entitlement (P23), crew and per-field merge (P19), push-triggered sync (P9 server part), the R2 lifecycle rule and deploys (owner).

## T-011a · `leavesDevice` and the sync and upload contracts · needs T-001a

**Goal.** The one rule for what may leave the device, and the shapes of sync and upload, exist as pure tested code both sides import.

**Do.**
1. `packages/story/src/leavesDevice.ts` (exported): `leavesDevice(moment, { cloudBackup })` → `{ row: boolean; media: 'none' | 'answer' | 'preview' | 'original' }` by the table above. Pure; `moment` is the `Moment` contract plus its asset's `kind`.
2. `packages/contracts/src/api/sync.ts`: `SyncedMediaAsset` (the `MediaAsset` fields minus `localPath`, `wrappedKey`, `posterPath`, `posterWrappedKey`, `uploadState`), `SyncChange` (a discriminated union on `entity`: `documentary`, `moment`, `mediaAsset`, `question`, `storyline`, `castMember`, each carrying its contract row), `SyncRequest { documentaryId, cursor: number | null, changes: SyncChange[] (max 100) }`, `SyncResponse { cursor: number, changes: SyncChange[], refused: { entity, id, reason: 'stale' | 'local_only' | 'not_yours' }[] }`.
3. `packages/contracts/src/api/uploads.ts`: `UploadPurpose` (`answer` | `preview` | `original`), `CreateUpload { assetId, purpose, contentType, bytes }`, `CreateUploadResult { uploadId, partSize: 5242880, partCount }`, `CompleteUpload { parts: { partNumber, etag }[] }`, `UploadDone { cloudKey }`.
4. `UploadJob` gains `purpose: UploadPurpose` (the device table follows in T-011e); `DOMAIN_SCHEMA_VERSION` goes up by one.

**Tests.** `leavesDevice` for every kind × `localOnly` × `cloudBackup` (a table test: localOnly gives `{ row: false, media: 'none' }` in every case); `SyncRequest` refuses 101 changes and a `mediaAsset` change carrying `localPath`; `SyncedMediaAsset` strips nothing silently (a row with `wrappedKey` fails to parse, it is not quietly dropped); `CreateUploadResult.partCount` for 0-byte is refused and for 5 MiB + 1 byte is 2 (a helper `partCountFor(bytes)` in contracts).

**Acceptance.** Story and contracts tests, typecheck, lint, format, boundaries pass; `packages/story` still imports only `@life/contracts` and `zod`.

## T-011b · `POST /sync` on the server · needs T-011a, T-010b

**Goal.** The server accepts a phone's changed rows for a documentary it owns, keeps the newer version of each row, refuses what may not leave the device, and returns everything changed since the phone's cursor.

**Do.**
1. Next D1 migration: tables for `moments`, `media_assets` (synced fields plus `cloud_key`), `questions`, `storylines`, `cast_members`, all keyed by the phone's UUIDs and carrying `documentary_id`, `updated_at`, `deleted_at`; `change_log (seq INTEGER PRIMARY KEY AUTOINCREMENT, documentary_id, entity, entity_id, updated_at)` with an index on `(documentary_id, seq)`.
2. `apps/api/src/policy/leavesDevice.ts` wraps the shared rule for the server (entitlement `cloudBackup: false` until P23).
3. `POST /sync` (`requireSession`; the documentary must belong to the user, else `403 forbidden`): for each change, refuse `not_yours` (a row whose `documentaryId` differs from the request's), `local_only` (by `leavesDevice`), or `stale` (stored `updatedAt` is the same or later); write the accepted rows and one `change_log` row each in one `batch()`; then return the rows whose latest `change_log.seq` is after the request's `cursor`, not counting the rows this request itself wrote, at most 500 per response, and `cursor` = the highest `seq` returned (or the request's, when nothing is newer). A `null` cursor returns everything.
4. The server never stores a device-only field (the contract parse already refuses them).

**Tests** (Workers pool, a signed-in user from T-010a's helpers): first sync with `cursor: null` stores the rows and returns an empty list and a cursor; a second phone of the same user pulls them; an older `updatedAt` is refused `stale` and the stored row is unchanged; a `localOnly` moment is refused `local_only` and nothing about it is stored; a row for another documentary is `not_yours`; another user's documentary gives 403; a tombstone (a moment with `deletedAt`) syncs as a change; 600 changed rows come back in two pages of 500 and 100 with increasing cursors; the rows written by a request are not echoed back to it.

**Acceptance.** API and contracts typecheck, tests, lint, format, boundaries, `deploy:dry` pass.

## T-011c · Sync on the phone · needs T-011b, T-010d

**Goal.** After sign-in, on every foreground and after each capture or edit, the phone pushes what changed and pulls what is new, and a restart continues from the stored cursor.

**Do.**
1. `src/data/repositories/syncState.ts` (rows in `settings`): the pull `cursor` and the push high-water mark `pushedUpTo` (an `updatedAt`); queries for the rows of each synced entity with `updatedAt` later than `pushedUpTo` (tombstones included).
2. `src/application/sync.ts`: `syncNow(store, clock, api, documentary)`: collect changed rows in pages of 100; drop every row `leavesDevice` refuses (and a media asset whose moment is refused); strip device-only fields; push; apply pulled changes with the same last-write-wins rule (a pulled row replaces the local one only when its `updatedAt` is later; a pulled media asset only updates an asset already on this phone, keeping its `localPath` and keys; a pulled moment whose media asset is not on this phone is skipped, per "One phone holds the media"); store the new cursor and `pushedUpTo` only after the whole round succeeds; one round at a time (a second call while one runs waits for it).
3. Triggers: the composition root calls `syncNow` when the app comes to the foreground and after sign-in; `captureMoment`, `tagMoment`, `editMoment` and `deleteMoment` callers in the routes call it after a successful change (never inside the use case, never blocking the screen). Signed out → it does nothing.

**Tests** (memory store, a fake Api that runs an in-memory copy of the server rule): a new capture is pushed once; a `localOnly` moment never appears in any push payload, nor does its media asset; device-only fields never appear in a payload (checked on the serialized JSON); a pulled newer row replaces the local one, an older one does not; a pulled moment whose media is not on this phone is not stored, and a pulled `cloudKey` lands on the local asset; a failed push leaves `cursor` and `pushedUpTo` unchanged so the next round sends the same rows; two overlapping calls make one round; after a "restart" (new Api fake, same store) the next round starts from the stored cursor.

**Acceptance.** Mobile typecheck, tests, lint, format, boundaries pass; UNVERIFIED: foreground sync on a device.

## T-011d · Uploads through the Worker · needs T-011b

**Goal.** The phone can create an upload for one of its assets, send it in 5 MiB parts, resume it, and complete it into R2; the server refuses anything `leavesDevice` refuses.

**Do.**
1. `POST /uploads` (`CreateUpload`): the asset must be synced, belong to the user's documentary, and its moment must allow exactly this `purpose` by `leavesDevice` (else `403 forbidden`, and for `localOnly` also nothing is created); starts an R2 multipart upload at the R2 layout key, stores `(assetId, purpose, uploadId, key, bytes, partCount)` in an `uploads` table (in the T-011b migration's successor), returns `CreateUploadResult`. Creating again for the same asset and purpose returns the same upload while it is open.
2. `PUT /uploads/:assetId/:purpose/parts/:n`: `n` within `partCount`; the body length must be exactly `partSize` for every part but the last (whose length is the rest); streams the body into `resumeMultipartUpload(key, uploadId).uploadPart(n, body)`; returns `{ partNumber, etag }`. Re-sending a part replaces it.
3. `POST /uploads/:assetId/:purpose/complete` (`CompleteUpload`): all parts present → `complete`, then the media asset's `cloud_key` is set and a `change_log` row written so phones learn it on the next sync; returns `UploadDone`. `DELETE …` aborts.
4. Body limits: parts only up to 5 MiB + a little; anything bigger is `400`.

**Tests** (Workers pool, R2 in Miniflare): a 12 MiB fixture in three parts (5, 5, 2) completes and the stored object's bytes equal the fixture (compare a SHA-256); a part of the wrong size is refused; completing with a part missing is refused; re-sending part 2 before completing still gives the right object; a `localOnly` asset is refused at create and no multipart upload is started; another user's asset gives 403; after completion a sync from `cursor` returns the asset with its `cloudKey`.

**Acceptance.** API and contracts typecheck, tests, lint, format, boundaries, `deploy:dry` pass.

## T-011e · The upload queue on the phone · needs T-011d, T-011c, T-009a

**Goal.** Captures that may leave the device are queued with their purpose and uploaded in the background of the app's life: on foreground, after capture and when the system runs the background task; uploads resume after a restart and wait politely on failure.

**Do.**
1. Next device migration: `upload_jobs` gets `purpose` and the primary key `(asset_id, purpose)` (SQLite cannot change a key in place: create the new table, copy the rows with `purpose = 'answer'` for answers' assets and delete the rows of any other asset, drop the old one; `upload_job_parts` follows), with its migration test from a seeded earlier version (rule 6).
2. `src/application/enqueueUploads.ts`: after `captureMoment` (the call site replaces the current unconditional enqueue): `leavesDevice` decides; `answer` → a job for the asset itself; `preview` → a preview file made with `PosterMaker.fromPhoto(uri, 1000)` (T-009a's port; JPEG 0.8), encrypted into the store like any file and recorded as the job's source; `none` → no job. Existing captures from before this task are enqueued once by the same rule on the first run.
3. `src/application/uploadQueue.ts`: `drainUploads(store, clock, api, network)`: jobs due (`nextAttemptAt` passed), oldest first, one at a time; video waits for Wi-Fi (`services/network`); decrypt the source to the cache, create or resume the upload, send the parts not yet recorded (read 5 MiB ranges with `FileIO.read`), record each part's etag as it succeeds, complete, mark the job `done`, remove the plain copy (also on failure); a failure sets `attempts + 1` and `nextAttemptAt` = now + min(2^attempts minutes, 6 hours); after 8 attempts the job is `failed` and kept for the next foreground (never dropped silently). One drain at a time.
4. `src/services/background/uploadTask.ts`: `TaskManager.defineTask` at module scope running one drain (a limited time budget, then stop), registered with `minimumInterval: 15` after sign-in; the composition root drains on foreground and after each capture.

**Tests** (memory store, fake Api with a fake R2, fake network): a video answer on cellular waits and uploads on Wi-Fi; a photo uploads a preview no larger than 1,000 px on its longest side (the fake poster maker records the size asked) and never the original; a clip enqueues nothing; a `localOnly` capture enqueues nothing and `drainUploads` never calls the Api for it; a drain that fails after part 2 of 3 resumes with part 3 only (the fake records the parts it received); backoff times after 1, 2 and 3 failures; after 8 failures the job is `failed` and still present; the plain copy is gone after success and after failure; the migration keeps every job and part.

**Acceptance.** Mobile typecheck, tests, lint, format, boundaries pass; `npx expo-doctor` no new failures; UNVERIFIED on a device: the background task running, a real upload over Wi-Fi and cellular, resume after the app is killed mid-upload.
