# T-014 · P13 Planner

Text for T-014a–d. Published 2026-09-27; this file does not change after publication. Fix lists are written in `tasks/TASKS.md` under the task.

## Preamble

**Goal of P13.** After understanding (P12), the pipeline turns the week into an episode plan: Claude Sonnet 5 reads the week brief and writes the plan's story part (title, scenes, bridges, tease, music mood, summary) under a fixed, cached style prompt. The server fills in everything else, checks the plan with `validatePlan` and the voice rules, retries once with the errors, and falls back to the recap plan so an episode always arrives (D20). The plan is stored, its summary feeds later briefs, and an evaluation runner scores the planner over the 20 fixture weeks. As in P12, model calls go through a port and everything is built and tested with a fixture planner; the real calls need the owner's Anthropic key.

**Read first:** `CLAUDE.md` (rules 1, 2, 3, 4, 5, 6, 8, 10, 11, 12), `docs/VISION.md` §5 and line 28 ("it never paraphrases the user"), `docs/design/DESIGN.md` §8, `docs/architecture/ARCHITECTURE.md` §4 "Episode plan", §5 "Episode", §6, §7, §9, DECISIONS D3, D10, D12, D20, D38, D39, `tasks/p12/T-013.md` (the pipeline, ports and providers this extends) and `tasks/p11/T-006.md` (the plan contract, `validatePlan`, `recapPlan`).

**Decided here (DECISIONS D39).**
- **Which numbers win.** The contract (`EpisodePlanV1`) and `validatePlan` are authoritative (T-006's decision): 3–5 scenes and 60–240 s in model mode. ARCHITECTURE §4's sketch is corrected to match.
- **The model writes only the story.** `PlannerOutput` (below) is what Sonnet 5 returns: title, subtitle, cold open, scenes (heading, storyline, shots, bridge), closing, tease, music mood, lower thirds, summary. The server adds `version`, `episodeNumber`, `weekStart`, `weekEnd`, `targetDurationMs` (from the shots), `captionsFromTranscript: true` on every scene (rule 14: captions on), and `narratorVoiceId`.
- **Narrator voice.** Our own ids `narrator-1` … `narrator-4` (P14 maps them to vendor voices and lets the person choose). Until then every plan with a bridge or a tease gets `narrator-1`, set by the server, never by the model.
- **Checks.** A model plan is kept only when `EpisodePlanV1` parses, `validatePlan(plan, brief, 'model')` passes, and `planVoiceErrors(plan)` is empty (model text is user-facing, so rule 11's banned phrases and characters apply to it). The first failure gets one more model call with the errors listed; a second failure, a refusal, a cut-off answer or a model error after the step's retry gives the recap plan. At most two answered model calls per episode.
- **An empty week.** A brief with no answer, clip or photo has nothing to show: no model call, no recap, and the episode row for that week is removed (quiet weeks are not failures, D2). A brief with media but no answer skips the model (the cold open must be an answer) and gets the recap plan.
- **Storage.** Plans are rows (`episode_plans`: episode, version, the plan JSON, `createdBy` `model` or `recap`, created at); the episode's `planVersion` points at the one in use and its `summary` is the plan's summary. Later briefs read the summaries of the documentary's last three episodes. Storyline summaries (T-008's mention) are later work.
- **Request.** `claude-sonnet-5` (one constant), adaptive thinking (the default, left on), effort `medium` (the eval compares `medium` and `high` before it is changed), `max_tokens` 16000 (below the SDK's non-streaming limit of about 21,333), the style prompt as one system block with `cache_control: { type: 'ephemeral', ttl: '1h' }` (Sunday runs of one time-zone bucket fall inside an hour), the brief JSON as the user message, and `output_config.format` built from `PlannerOutput`. No user data in the system block (caches are shared across users in the workspace). No temperature, no prefill (both are 400 on Sonnet 5).
- **Costs.** One ledger row per episode, step `plan` and unit, at Sonnet 5 prices: input 2 µUSD, output 10 µUSD, 1-hour cache write 4 µUSD, cache read 0.2 µUSD per token (thinking is billed as output). T-013b's note widens the ledger enums for this.
- **Workflow state.** Plan steps return outcomes, versions, error strings and token counts only. The brief and the plan text never go into a step result (Workflow state is kept for 30 days); a step reads what it needs from D1 and writes what it makes to D1.

**Stack (checked 2026-09-27).**
- Sonnet 5: model id `claude-sonnet-5` (dateless, pinned); $2 / $10 per MTok; cache write 1h $4, read $0.20; 1M context; 128K output. Structured outputs are GA: `output_config: { format: { type: 'json_schema', schema } }`. Schema limits: `additionalProperties: false` on every object, `minItems` only 0 or 1, no `minLength`/`maxLength`/`minimum`/`maximum`/`maxItems`; at most 24 optional properties and 16 union-typed properties per request; a schema that is too complex is a 400. Output can still miss the schema on `refusal`, `max_tokens` or `model_context_window_exceeded`, and enum casing is not guaranteed.
- `@anthropic-ai/sdk` 0.128.0 (P12's pin): `zodOutputFormat(schema)` from `@anthropic-ai/sdk/helpers/zod` needs a Zod 4 schema and moves every keyword the API does not support (including `enum`, `const`, lengths and bounds) into the description text, so only the object shape is enforced by the API and our own Zod parse is what checks the rest. Use `client.messages.create({ …, output_config: { format: zodOutputFormat(PlannerOutput) } })`, not `messages.parse` (which throws before the caller can read `stop_reason`). `stop_reason` values: `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, `model_context_window_exceeded`. `usage` has `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`.
- Prompt caching: the minimum cached prefix on Sonnet 5 is 1,024 tokens; a shorter one silently does not cache. The cache key covers the format, the system block, thinking and effort settings: any byte change there starts a new cache.
- The test pool: as in P12 (`remoteBindings: false`, fixtures only with `PROVIDERS: 'fixture'`, Workflow introspection with `dispose()` in `finally`). The eval runner runs in Node, not the Workers pool (it calls the real API from the owner's machine).

**`PlannerOutput`** (`packages/contracts/src/episode/plannerOutput.ts`; reuse the shot, Ken Burns and music mood schemas of `plan.ts` by export, no copies):
```
title: string 1..60
subtitle?: string 1..80
coldOpen: { momentId, inMs ≥ 0, outMs ≥ 1 }            (outMs > inMs)
scenes: 3..5 × { heading 1..60, storylineId?, shots: 1..6 × Shot, narratorBridge?: { text 1..140 } }
closing: { momentId }
tease?: { storylineId, text 1..100 }
musicMood: MusicMood
lowerThirds: 0..20 × { momentId, castId, atMs ≥ 0 }
summary: string 1..400
```

**The style prompt** (`apps/api/src/pipeline/plan/stylePrompt.ts`, exported as one constant, sent unchanged as the system block):

> You plan one episode of a personal documentary. The person records a short answer to one question each day and adds photos, clips and notes. Once a week you turn their week into an episode of two to four minutes. Their own recorded answers are the heart of it. You arrange what they recorded. You never put words in their mouth.
>
> You get the week as JSON: the moments in order, each with its day, its kind (answer, clip, photo or note), its length, the question it answers, a transcript of what they said when there is one, a plain description of the picture when there is one, their own note, their mood if they set one, and the storylines and people they tagged. You also get the summaries of up to three earlier episodes, so the story can carry on from where it was.
>
> Your answer is the plan, in the shape you're given. Every moment you use must be one from this week's list, named by its id. Use only what is there. Don't invent places, people, times or events, and don't fill a gap with a guess.
>
> How an episode goes. It opens cold on a few seconds of one answer, the strongest line of the week, and that must be an answer. Then the title. Then three to five scenes, grouped by storyline where the week has one, otherwise by day, in the order things happened. Each scene has a short heading and one to six shots. An answer usually plays whole. You may trim it with inMs and outMs to the part that matters, but never past its length. A photo can drift slowly with kenBurns, both scales between 1 and 1.5. A clip plays a few seconds. The episode ends on a closing shot that lets the week settle. Add a tease of next week only when a storyline is still open, in one line. Add a lower third only for a person the person tagged in that moment, by their cast id, at the point in the episode where they appear.
>
> Answers and storylines. Most answers are about ten seconds long. Keep the whole answer unless its start or its end is only a pause or a false start, and never cut a sentence in half. When a storyline runs through the week, give it a scene of its own and put its id on that scene. When an earlier summary mentions a storyline that moved this week, a bridge may say where it stands now. When nothing moved, leave it out. Notes have no picture or sound, so they never appear as shots, but they can tell you what a day was about.
>
> The narrator. The person's own voice carries the episode. The narrator only links scenes with a short bridge, at most one per scene, and says the tease. Everything the narrator says, taken together, must stay well under a quarter of the time anyone is speaking in the episode. When in doubt, leave the bridge out. A bridge frames the scene: the day, the place, where a storyline stands. It never retells what the person said, never quotes them, never sums them up and never guesses how they felt. Their words stay theirs. Good bridges: "Tuesday. The plumber still hasn't come." "Saturday, at the allotment." "Three weeks into the new job."
>
> Words. Everything you write is read or heard by the person, so it has to sound like a careful person wrote it. Plain, calm and specific. Short words. Contractions where you'd say them. Sentence case for the title and the headings: "The week the kitchen flooded", not "The Week The Kitchen Flooded". British spelling. No exclamation marks, no dashes of any kind between words, no semicolons and no emoji. No stock phrases and nothing that sounds like an advert, a coach or a chatbot: no "journey", "unforgettable", "a week to remember", "moments that matter", "at a glance", "embrace", "unlock", "cherish" or "vibes". Don't write a poetic line where a plain one works. No guilt and no games: never mention missed days, streaks, scores or goals. Never say or suggest that anything recognised a face or a voice. People are named only by the names the person gave them, and places only by the names the person gave them.
>
> The title says what this week was about, in the person's own world: "The week the kitchen flooded", "Mum's first week home", "Rain, and the new bike". Never a generic title such as "My week", "This week", "Week 12", "A week in review", "Highlights" or "Weekly recap". The subtitle, when you add one, is a short plain line under it.
>
> The summary is two or three plain sentences about what happened this week, written for the next episodes to build on. It states only what the week shows, in the third person, with no judgement of how the week went.
>
> Music. Pick the one mood that fits the week as a whole: calm, warm, bright, bittersweet or driving.
>
> A thin week is fine. Make a short, honest episode from what there is. Don't pad it and don't invent anything to fill it.
>
> If the list of errors from an earlier attempt follows the week, fix every one of them and keep the rest of the plan as it was.

## T-014a · The planner's shapes and checks · needs T-013b

**Goal.** The pure parts of planning exist and are tested: what the model returns, how the server completes and checks it, and the properties the evaluation scores.

**Do.**
1. Contracts: `PlannerOutput` as above; `StoredPlan { episodeId, version: int ≥ 1, plan: EpisodePlanV1, createdBy: 'model' | 'recap', createdAt }`; `plan.ts` exports the shot, scene-bridge and lower-third schemas it already has so `PlannerOutput` reuses them.
2. `packages/story/src/plan/duration.ts`: `shotMs(shot, moment)` = (`outMs` ?? the moment's full length) − (`inMs` ?? 0), where the full length is `recapPlan`'s current rule (answer: `durationMs` ?? 6000; clip: min(`durationMs` ?? 6000, 6000); photo: 3000); `recapPlan` uses it instead of its private copy (its results do not change). `planDurationMs(plan-like, brief)` = 3000 (title) + the cold open's span + Σ `shotMs` + 2500 (closing), clamped to 20,000..240,000, as `recapPlan` does today.
3. `assemblePlan(output, brief, { narratorVoiceId })` → `EpisodePlanV1` (parsed): `version: 1`, `episodeNumber`, `weekStart`, `weekEnd` from the brief, `targetDurationMs` from `planDurationMs`, `captionsFromTranscript: true` on every scene, `music: { mood: output.musicMood }`, `narratorVoiceId` only when a bridge or a tease exists. It throws when the result does not parse (the caller treats that as an invalid plan).
4. `planVoiceErrors(plan)` → strings: for the title, subtitle, each heading, each bridge, the tease and the summary, one error per banned phrase (`voiceBannedPhrases`, whole words, any case) or banned character (`voiceBannedCharacters`) found, naming the field (for example `scene 2 bridge uses ";"`). Error strings name fields and the banned item only, never other text of the plan.
5. `narratorShare(plan, brief)` → the narrator's share of spoken time by `validatePlan`'s own rule (move the arithmetic into one exported function that `validatePlan` also calls; its results do not change).
6. `planProperties(plan, brief)` → `{ valid, userVoiceShare, coldOpenIsAnswer, momentsFromBrief, titleNotGeneric, noCopiedWords, voiceClean }`: `valid` = `validatePlan(…, 'model').ok`; `userVoiceShare` = 1 − `narratorShare`; `momentsFromBrief` = every moment id is in the brief; `titleNotGeneric` = the title is not the week's recap title and does not match (any case) `my week`, `this week`, `the week`, `a week`, `week <n>`, `episode <n>`, `a week in review`, `week in review`, `weekly recap`, `highlights`; `noCopiedWords` = no bridge and no tease shares a run of 5 or more consecutive words (case and punctuation ignored) with any transcript in the brief; `voiceClean` = `planVoiceErrors` is empty.
7. Move `packages/story/test/fixtures/weeks.ts` to `packages/story/src/fixtures/weeks.ts`; `packages/story/package.json` exports it as `"./fixtures"` (not from the main index); existing tests import it from there.

**Tests.** `PlannerOutput` refuses 2 scenes, 6 scenes, 7 shots in a scene, a 141-character bridge, a 401-character summary and an unknown music mood; `assemblePlan` on a fixture output sets the brief's week and number, `captionsFromTranscript: true` everywhere, `narratorVoiceId` only with a bridge or tease, and a `targetDurationMs` equal to `planDurationMs`; `recapPlan` gives exactly the same plans for all 20 fixture weeks as before the move (snapshot each week's plan before refactoring and compare); `validatePlan` gives the same results for its existing tests; `planVoiceErrors` finds `—`, `;`, `!` and a banned phrase in a heading, and nothing in a clean plan; `planProperties` on a hand-made plan per property (a generic title, a bridge copying five words of a transcript, a cold open on a photo, a narrator share over 25%) flags exactly that property.
Allowed test changes: imports of the fixture weeks change path; none removed or loosened.

**Acceptance.** Contracts and story typecheck, tests, lint, format, boundaries pass; `packages/story` still imports only `@life/contracts` and `zod`.

## T-014c · EpisodePipeline step 2: plan · needs T-013d, T-014a, T-014b

**Goal.** After understanding, the pipeline plans the episode: a checked model plan, one retry with the errors, the recap plan when that fails, nothing for an empty week; the plan, the summary and the cost are stored.

**Do.**

The next D1 migration: `episode_plans` (the `StoredPlan` fields, the plan as JSON text; unique `(episode_id, version)`), with its migration test. `data/repositories/plans.ts`: `put(storedPlan)` (upsert by episode and version), `current(episodeId)`. `episodes.ts` gains `setPlan(episodeId, version, summary, state)` and `remove(episodeId)` (the episode, its plans and its ledger rows).

4. `EpisodePipeline.ts`, after the understand steps: `plan-brief` (returns only whether the brief has an answer and whether it has any media); when it has no media → `plan-empty` (remove the episode) and the run ends; when it has media but no answer → `plan-recap`; otherwise `plan-1` (`retries: { limit: 1 }`), then `plan-2` with `plan-1`'s errors when `plan-1` was `invalid`, then `plan-recap` when neither stored a plan (a refusal goes straight to `plan-recap`; a step that still throws after its retry is caught and also goes to `plan-recap`); `plan-costs` (one ledger upsert per unit with units above 0, summed over the attempts, by `planMicroUsd`, then `costCents`).

**Tests** (Workers pool, D1 in Miniflare, the fixture planner). A valid first answer is stored as version 1 `model`, the episode has its `planVersion`, `summary` and state, and the planner was called once with the style prompt as the system text; an invalid first answer then a valid second one: two calls, the second's user text ends with the first's errors, the stored plan is the second; two invalid answers: the recap plan is stored and the state is `rendering`; a refusal: one call, then the recap; a planner that throws on every attempt: the recap; a week with photos and no answer: no planner call, the recap; a notes-only week: no call, the episode and its rows are gone; the brief of episode 4 carries the summaries of episodes 1–3, and a `localOnly` moment's note and transcript (seeded in D1) never appear in any planner call's user text; ledger rows for `plan` sum both attempts' tokens and `costCents` includes them; a replayed run (Workflow introspection) stores one plan and one set of ledger rows.

## T-014d · The planner evaluation · needs T-014c

**Goal.** One command runs the real planner over the 20 fixture weeks and prints how each plan scores, so a prompt or model change can be judged before it ships.

**Do.**
1. `apps/api/eval/planner.eval.ts`, run by `pnpm --filter @life/api eval:planner` (a Node Vitest config `apps/api/eval.config.ts`, never part of `pnpm test` or CI): for each fixture week (from `@life/story/fixtures`), build the brief with episode number 1 and no earlier summaries, run the same `attempt` logic as T-014c against the real planner (its D1 writes go to an in-memory stand-in, never a real database), and score the resulting plan with `planProperties`.
2. Expectations per week: a week with an answer expects a model plan with every property true and `userVoiceShare` ≥ 0.75; a week with media but no answer expects no model call and the recap; a week with no media expects nothing. A week passes when its expectation holds.
3. Output: a Markdown table on stdout (week, expectation, outcome, each property, input, output and cache tokens, µUSD), then the totals (weeks passed, total µUSD). Options: `--effort=low|medium|high` and `--week=<n>`. Without `ANTHROPIC_API_KEY` it prints `Skipped: ANTHROPIC_API_KEY is not set.` and exits 0.
4. `docs/architecture/EVALS.md`: what the evaluation checks and why (the properties above), how to run it, and a results table with one empty row "not run yet: needs the owner's key".
5. A normal test (in `pnpm test`): the runner's scoring and table code, driven by the fixture planner, gives 20 rows whose expectations match the fixture weeks (weeks with and without answers and media).

**Acceptance.** API typecheck, tests, lint, format, boundaries pass; `eval:planner` without a key prints the skip line and exits 0. UNVERIFIED until the owner's key: a real run, recorded in `EVALS.md` by the supervisor.
