## Preamble

**Goal of P17.** The person changes a delivered episode with one tap per change, and the new cut replaces the old one.
- The five changes: rename it, swap a narrator line for one of their answers or for their own words, take out a clip, pick the last shot, change the music.
- Each change is a pure edit of the stored plan, saved as a new plan version.
- The server re-narrates only the lines that changed, re-cuts the newest plan, and swaps in the new video when it is done.
- A re-cut that fails is undone, and the app says so.
- Ten changes per episode per day.

**Decided here (DECISIONS D43).**

- **What each change does.**
  - These are pure rules in `packages/story/src/editOps`. `applyEdit(plan, change, brief)` returns the new plan or a refusal reason.
  - **Rename** (`retitle`): the title, trimmed, 1 to 60 characters.
  - **Swap a line for an answer** (`swapLine` with a `moment`). The checks run in this order:
    1. `noScene`;
    2. `noLine`, when the scene has no narrator line;
    3. `notAnAnswer`, unless the moment is an answer in the rebuilt brief;
    4. `alreadyIn`, when the cut already shows it (as the cold open or a shot);
    5. `sceneFull`, when the scene has 6 shots.

    The line is removed and the answer becomes the scene's first shot (`shotFor`). The change's `inMs` and `outMs` are used when given, inside the answer's length.
  - **Swap a line for the person's own words** (`swapLine` with a `bridge`):
    - The scene's line becomes the person's text, trimmed, 1 to 140 characters. A scene without a line gets one.
    - It needs the plan's narrator voice, so a recap can't take one (`noNarrator`).
    - It may not contain a digit (`hasNumbers`, from `speakable`), because the voice reads digits badly.
    - It is refused as `narratorTooLong` when the new line raises the narrator's estimated time (`narratorShare`) and the result is above a quarter. A shorter line is always allowed.
    - The person's own words are not held to the model's voice and copy rules (`planVoiceErrors`, `planCopyErrors`).
  - **Take out a clip** (`dropClip`):
    - The shot is removed. A scene left without shots is removed with its line.
    - The episode's last remaining shot can't go (`lastShot`).
    - A lower third whose moment no longer appears in any shot is removed.
    - When the moment taken out is the closing's, and neither the cold open nor a remaining shot shows it, the closing becomes the moment of the last remaining shot. A closing that was never in the cut is left as it is.
  - **Last shot** (`closingShot`): a moment the cut already shows, as the cold open or a shot (`notInCut` otherwise). The closing is picked from the episode's own footage, so no upload is needed.
  - **Music** (`musicMood`): the mood changes and `trackId` is cleared.
  - **Length.**
    - After every change, `targetDurationMs` becomes `planLengthMs(plan, brief)`, clamped to 20 s to 240 s.
    - Only a take-out that brings the unclamped length under 20 s is refused (`tooShort`). Only an answer swap that takes it over 240 s is refused (`tooLong`).
    - Other changes never fail on length, so a short recap can still be renamed.
  - **`unchanged`.** A change that leaves the plan as it was is refused as `unchanged`. This is checked before `targetDurationMs` is rewritten.
  - **Other refusals.** An index out of range gives `noScene` or `noShot`, and a result that doesn't parse as `EpisodePlanV1` gives `doesNotFit`.
  - Only moments still in the rebuilt brief can be brought in, so a `localOnly` or deleted moment never is (rule 8).

- **Versions.**
  - An applied change is stored as plan version n+1 (`createdBy: 'edit'`), together with its edit row, in one D1 batch with a plain insert.
  - Plan versions only grow.
  - A change names the version it was made on (`appliedToVersion`). When that is not the current version, the answer is `stale`, with the current cut.
  - An edited or reverted episode keeps the origin of the plan it came from: `model` or `recap`. So an edited model episode still reaches later weeks' briefs.

- **One re-cut at a time, always of the newest plan.**
  - A new Workflow, `RecutPipeline`, runs the re-cut, with the run id `recut-{episodeId}-v{n}`.
  - The edit's batch claims `episodes.recut_run` only when it is empty. The request that claimed it starts the run with `createBatch`, which skips an id that already exists.
  - When a run is already going, the edit sends it `originals-ready` as a wake-up, so a run that is waiting looks again.
  - Any error from `get`, `sendEvent` or `createBatch` is ignored where a route sends or starts something (an instance that is missing, complete or errored), because the cron recovers the claim.
  - Each round of the run:
    1. narrates the newest version (clips are cached by hash, so only changed lines cost anything);
    2. makes sure the answers the edits brought in have arrived;
    3. renders that version.
  - At the end of a round, a conditional update clears `recut_run` only if the plan hasn't moved on. Otherwise the run goes round again with the newest version.
  - So a change made during a re-cut that works is never lost and never cut twice at the same time.
  - The 15-minute cron starts again any claimed run whose instance is missing, and undoes any whose instance has ended without releasing the claim.

- **The old cut plays until the new one is ready.**
  - The episode stays `ready` throughout. `checkRender` sets the new render version when the render is done (D41).
  - The video route takes a render version (`?v=`), so a player keeps getting the bytes it started with. The phone switches to the new version when sync brings it.
  - The previous render file is kept for 30 minutes after a re-cut ends, then deleted, along with any older ones.
  - No push is sent for a re-cut. The app learns of it through sync.

- **A re-cut that fails is undone.**
  - When narration, the wait or the render fails, one D1 batch stores the published plan (the plan of the current render) as the next version, with `createdBy: 'revert'`, marks the re-cut `failed` and releases the claim. The run then tidies and ends. A change made after that batch claims a new run of its own.
  - This undoes every change since the published cut, including changes made during the failing round. So the stored plan always matches a video or is being cut.
  - The app says: "Couldn't make that change. The episode is as it was."

- **Swapped-in answers.**
  - An answer the episode didn't use has no original in the cloud, because its working copy was deleted after planning (D42).
  - The edit opens an original request for it. It reopens a closed or met row whose original is gone.
  - At each check, the run itself also reopens a request for every answer the plan shows that the published plan doesn't and that has no original. The run doesn't depend on the route's timing.
  - `leavesDevice` lets an answer with an open request upload its `original` (rule 8 holds: never a `localOnly` one).
  - The phone sends it straight away, since the person is in the app. A voice answer goes on any network. A video answer waits for Wi-Fi (D37), and the app says so.
  - The run waits until 24 hours after the round's first check, then undoes the change.
  - A request for an answer the newest plan no longer shows is closed, so taking the answer back out ends the wait.

- **What stays in the cloud** (VISION §8).
  - After a re-cut is published, and after a re-cut is undone, the run deletes the originals of the week's moments that neither the published plan nor the current plan shows. It closes the requests of the originals it deleted, so the phone drops its finished job and a later request uploads again.
  - Narration clips stay: they are small, and a change back reuses them.

- **The limit.**
  - 10 applied changes per episode per local day, in the documentary's time zone (`localDay`).
  - Refused and stale changes don't count.
  - It lives in `apps/api/src/policy/edits.ts`.

- **Costs.**
  - Re-narration has its own ledger row (step `renarrate`, unit `character`), rebuilt from the characters each round recorded, so a replayed round never counts twice.
  - Render costs keep adding up across renders (D41).

- **The phone.**
  - The cut comes from `GET /episodes/:id/cut` and is not synced, since changes need a connection anyway.
  - `EpisodeSummary` carries `recut` (`working`, `waiting` or `failed`).
  - After every applied change the phone syncs, and the Episode screen then syncs every 15 s while a re-cut is under way and the screen is open, for up to 20 minutes.

## T-018b · The re-cut run · needs T-017c, T-017e, T-017f, T-018a

**Goal.** Once a change is stored, a Workflow cuts the newest plan and swaps in the new video. It tidies what the old cut used, and undoes the change when it can't be cut.

**Do.**

1. **Storage.**
   - The next D1 migration adds, with its migration test:
     - `episodes.recut_state` (`working`, `waiting` or `failed`; nullable);
     - `episodes.recut_run` (text, nullable);
     - `recut_narration` (`episode_id` cascading, `plan_version`, `characters`; unique on episode and version).
   - `data/repositories/episodes.ts` gains:
     - `setRecutState(id, runId, state, at)`, only `WHERE recut_run = runId`;
     - `endRecut(id, runId, planVersion, at)`, which clears both columns only `WHERE recut_run = runId AND plan_version = planVersion`, and returns whether it did;
     - `failRecut(id, runId, at)`, batch items that set `failed` and clear `recut_run`, only `WHERE recut_run = runId`.
   - Every change to these columns writes a change-log row, so the summary syncs. `EpisodeSummary.recut` is filled from `recut_state`.
   - `data/repositories/plans.ts` gains:
     - `insert(db, stored, opts?)`, a batch item with no on-conflict clause. Without `opts` it is a plain INSERT, for the edit route. With `{ whileRun: runId }` it is `INSERT … SELECT … WHERE EXISTS (SELECT 1 FROM episodes WHERE id = ? AND recut_run = ?)`, with the version still explicit, so a clash still throws;
     - `get(db, episodeId, version)`.

     `put` stays as it is for the weekly run.
   - `data/repositories/originalRequests.ts` gains `reopen(episodeId, rows)`, which sets rows open whatever their state, with a change-log row. It also returns batch items, for T-018c.
   - `data/repositories/brief.ts` `previousSummaries`: an earlier episode counts when its plan versions include a `model` version and no `recap` version. Edits and reverts keep the origin of the plan they came from.
2. **A version for narration and render.**
   - `linesStep(ctx, episodeId, planVersion?)`: with a version, it returns that version's lines when it is the current plan, whatever the episode's state.
   - `fitStep` moves the episode to `rendering` only from `narrating`.
   - `startRender(ctx, episodeId, format, planVersion?)` reads the version once: the given one, or `episode.planVersion` when none is given.
     - A given version that is not the current plan gives `{ outcome: 'stale' }`.
     - It passes that version to `renderInput(ctx, episode, format, version)`, which draws `plans.get(db, episodeId, version)` with that version's narration instead of `plans.current`.
     - The render row and the same-version lookup use that version too, so an edit landing during a start can't mix two versions.
   - Called without the new arguments, each behaves as before.
   - `CostLedgerRow.step` gains `renarrate`.
3. **`pipeline/recut/RecutPipeline.ts`.** Params `{ episodeId, runId }`. Up to 20 rounds r:
   1. **`recut-begin-{r}`.** It ends the run when the episode is not `ready` or its `recut_run` is not `runId`. Otherwise it sets `working` and returns the current plan version v.
   2. **Narration**, when the plan has lines: `recut-lines-v{v}`, `recut-line-v{v}-{i}`, `recut-fit-v{v}`.
      - Then `recut-narrate-costs-v{v}` upserts this round's spoken characters into `recut_narration`.
      - It sets the `renarrate` ledger row to their sum, and the episode's cents.
   3. **Originals.** `recut-deadline-v{v}` returns now + 24 h. Then checks `recut-originals-v{v}-{w}`, for w from 0 up to 50. Each check:
      - goes to the next round when `plan_version` is past v;
      - reopens a request for every answer that plan v shows (cold open, shots or closing), that the published plan doesn't show, that the rebuilt brief still has, and whose `u/…/{asset}/original` is not in R2;
      - closes the open requests for assets plan v doesn't show;
      - counts the rest. None: set `working` and render. Some: set `waiting` and return the time left before the deadline.

      Between checks, `waitForEvent('recut-wait-v{v}-{w}', { type: 'originals-ready', timeout: time left })` runs in try/catch. An event, whether early, buffered or a wake-up, only leads to the next check. The deadline passing with requests still open, or the 50 checks used up, is a failure.
   4. **Render.**
      - `recut-render-start-v{v}` (portrait, version v), with the weekly run's retries.
      - Then rounds of `recut-render-sleep-v{v}-{n}` (20 s) and `recut-render-check-v{v}-{n}`, at most 45.
      - `stale` goes to the next round.
      - `nothing`, `failed`, a throw after retries, or the round limit is a failure.
   5. **`recut-replace-v{v}`.** It runs `tidyOriginals` and deletes the R2 files of every done render of the episode below the current render version minus 1, in both shapes.
   6. **`recut-end-v{v}`.** `endRecut`. When it cleared, the run goes to step 7. Otherwise the next round starts.
   7. **`recut-keep-old`.** A 30-minute sleep, then `recut-drop-old` deletes the R2 files of every done render of the episode below the current render version (read then), in both shapes.

   **`tidyOriginals(ctx, episodeId, runId)`.** For each moment of the week that neither the published plan nor the current plan shows (both read when it runs), it deletes `u/…/{asset}/original`, unless `leavesDevice` allows it with Cloud backup. It closes that asset's requests. A missing object is ignored, so a replay deletes nothing more.

   **Failure** (in any round, from the top-level catch, or when the 20 rounds are used up) runs two steps:
   - **`recut-revert`**, one D1 batch whose statements all apply only while `recut_run = runId`:
     - it stores the plan of the current render (`plans.get`) as the next version, with `plans.insert(…, { whileRun: runId })` and `createdBy: 'revert'`, unless that is already the current plan;
     - it sets `plan_version`;
     - it closes the episode's open requests;
     - it runs `failRecut`, which releases the claim in the same batch.

     A clash with an edit landing at the same moment throws, and the step's retry stores the revert at the next version. After the batch, a new change finds the claim empty and starts its own run.
   - **`recut-revert-tidy`**: `tidyOriginals`. An original it deletes that a newer plan shows is asked for again by that run's check.
4. **Starting and resuming** (`pipeline/recut/start.ts`):
   - `startRecut(env, episodeId, runId)` calls `RECUT_PIPELINE.createBatch([{ id: runId, params }])`.
   - `resumeRecuts(env)` runs for every episode with a `recut_run`. `scheduled` calls it after `startDueWeeks`. For each one:
     - an instance that doesn't exist is created again with `createBatch`;
     - an `errored` or `terminated` instance, or a `complete` one whose claim is still set, gets the failure work run directly with that run id: the revert batch, then `tidyOriginals`;
     - anything else is left alone.
   - The binding is added to `wrangler.jsonc`, `Env` and `index.ts`, and the types are regenerated.
5. **The upload route.** When an `original` completes and meets an episode's last open request, `originals-ready` also goes to that episode's `recut_run` when set.
